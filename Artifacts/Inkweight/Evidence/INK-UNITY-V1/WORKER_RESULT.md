## 6. Observations about the JavaScript core, shared files and golden files

No golden value looked wrong; every one of them was reproduced exactly. Points
for the Director or the Reviewer, none of them changed by this order:

1. `INK_RULES_V1.md` section 3 still shows the first formulas (armour `20 + 2 *
   C + 0.25 * N`, sharpness `3 + 0.12 * S`, top speed `9 / (1 + N / 160)`,
   blunt damage 1, cooldown 0.4 s). `ink_tuning.json` and the golden files use
   55 / 2 / 0, a squared sharp-share term, 38 and 70, 1.2 and 24 ticks. The
   document itself says the JSON wins and the text must be corrected by a Work
   Order.
2. Negative zero: at round start a front vector component can be `-0` (for
   example `-slot[1]` with slot `[-1, 0]`). The state hash covers the sign bit,
   the JSON body rows cannot (`JSON.stringify(-0)` is `0`). Both
   implementations agree, so nothing is wrong, but a port that compares only
   the body rows would not notice a sign difference; the hash is the binding
   comparison.
3. `core/ring.js` `ringStep` counts `outNow` and never uses it (harmless).
4. Several tuning values are used as loop bounds, array indices or modulo
   operands (`bossEscortCopies`, `beats`, `wobbleTicks`, `stakes`). The C# port
   keeps them as doubles and follows the JavaScript semantics for the current
   values; a later non-integer value for such a field would be an untested
   corner in both implementations.
5. Balance hint from the smoke run, not a measurement: with example drawings
   and an almost idle hero (one key toggled, no aiming) the solo run was won in
   all twelve smoke runs whose outcome was looked at, boss included. The solo numbers may be too
   kind.

## 7. Known weaknesses

- Bit-exactness is proven on .NET 8 x64 only. Unity's Mono on x64 very likely
  behaves the same. IL2CPP translates to C++, and C++ compilers for ARM64
  (phones, Apple silicon, consoles) may by default fuse `a * b + c` into one
  operation, which changes last bits. C# cannot forbid that in source. The menu
  self check shows it per build; if it fails on a target, the fix is a compiler
  setting or a different build option, to be decided then.
- `double.Parse` of the tuning text happens at run time in Unity. Short
  decimals like the present values parse exactly on every runtime I know; the
  self check would show a deviation.
- The engine stand-ins come from memory. Typical first-open risks: a member
  name, the optional assembly reference, the `inputlegacy` module name in a
  future Unity version, GUI scaling of mouse coordinates.
- Presentation is deliberately plain: immediate-mode GUI, no paper look, no
  wobble, squash or sound, no drawing timer (the 30 s of `drawTimeSeconds` is
  not enforced), bots use fixed example drawings, only seat 0 is human, no
  local multi-player, no save.
- Touch: one finger steers (left half) and another dashes (right half); written
  blind.
- The Runtime layer allocates per tick (input arrays, lists in the solo step,
  as in the JavaScript original). Fine for a prototype, not for mobile.
- `Dictionary` enumeration order is used by the generator for the order of the
  example drawings; it is insertion order in practice, not by contract.
